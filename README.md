## Проблема

У бизнеса есть реальные проблемы, но исходный запрос часто выглядит как «хотим увеличить продажи» или «нужно автоматизировать процесс». Команде трудно начать работу без понимания данных, ограничений, ожидаемого результата и критериев успеха.

Студентам, в свою очередь, нужны понятные практические задачи: что предстоит сделать, какие навыки пригодятся и кто со стороны компании готов обсуждать результат. Между бизнес-идеей и совместной работой не хватает ясной постановки задачи.

## Наше решение

**Qadam** — «шаг» на казахском. Бизнесу достаточно описать проблему своими словами. Система помогает уточнить детали, собрать карточку и оценить её полноту. Дальше задача попадает в каталог, команды предлагают решения, а бизнес выбирает исполнителей и подтверждает результаты работы.

Например, запрос «после обеда падают продажи в кофейнях» становится задачей с описанием выгрузки чеков, ожидаемым дашбордом, измеримым критерием успеха и контактом представителя компании.

## Основной сценарий

```text
Идея → Уточняющие вопросы → Карточка → Рейтинг → Публикация
                                                    ↓
                            Подтверждение этапов ← Отклики команд
```

| Шаг | Действие | Результат |
| --- | --- | --- |
| 1. Описать | Бизнес вводит черновик и выбирает отрасль | Исходный контекст задачи |
| 2. Уточнить | Система задаёт вопросы, бизнес отвечает | Данные для заполнения пробелов |
| 3. Подготовить | Система собирает карточку и рассчитывает рейтинг | Структурированная задача с подсказками |
| 4. Опубликовать | Бизнес проверяет карточку и подтверждает публикацию | Задача в общем каталоге |
| 5. Выбрать команду | Команды присылают предложения, бизнес рассматривает их | Принятые или отклонённые отклики |
| 6. Подтвердить этап | Бизнес подтверждает выполненную работу | +10 баллов команде за каждый этап |

## Что умеет Qadam

| Для бизнеса | Для студенческих команд |
| --- | --- |
| Превращать свободное описание в структурированную задачу | Смотреть каталог опубликованных задач |
| Получать уточняющие вопросы и подсказки по заполнению | Получать рекомендации по навыкам, технологиям и интересам |
| Видеть рейтинг готовности с объяснением каждого балла | Предлагать идею, план, сроки и ссылку на прототип |
| Редактировать карточку и публиковать её вручную | Набирать баллы за подтверждённые этапы работы |
| Принимать или отклонять отклики команд | Видеть решение бизнеса по отклику |

**ИИ помогает сформулировать задачу.** Рейтинг рассчитывается по открытым правилам, рекомендации — по совпадению ключевых слов. Решения о публикации, выборе команды и подтверждении этапов принимает человек.

### Состояние MVP

Серверная часть реализует полный сценарий через REST API и Swagger UI. По умолчанию она работает без ключа и вызовов внешней модели, с демонстрационными данными.

В веб-интерфейсе пока остались маркеры конфликта слияния в `index.html`, `app.js`, `styles.css` и `favicon.svg`. Бизнес-фасад [`api.mjs`](src/main/resources/static/api.mjs) использует отдельный mock-сервис с хранением в браузере и ещё не подключён к REST API. **Для демонстрации текущей версии используйте Swagger UI.**

### Локально через Maven Wrapper

Нужен **JDK 21**. Maven отдельно устанавливать не требуется; при первой сборке Wrapper загрузит Maven и зависимости.

```bash
# macOS / Linux, из корня проекта
./mvnw spring-boot:run
```

```powershell
# Windows
.\mvnw.cmd spring-boot:run
```

По умолчанию при старте создаются **10 задач** — 5 черновиков и 5 опубликованных, **5 команд** и **5 откликов**. Данные синтетические, внешняя модель для их создания не вызывается.

База H2 хранится в памяти: после остановки приложения изменения теряются. При следующем запуске демо-данные создаются заново.

## Демо-сценарий

Пройдите путь от идеи до первого подтверждённого этапа в [Swagger UI](http://localhost:8080/swagger-ui.html). Сценарий рассчитан на режим `mock` с включёнными демо-данными.

### 1. Опишите проблему

Выполните `POST /api/tasks/analyze`:

```json
{
  "draftText": "Мы сеть из 12 кофеен в Алматы. Хотим понять, почему в будни после обеда падают продажи. Есть выгрузка чеков из кассовой системы за 2 года в Excel.",
  "industry": "HORECA"
}
```

В ответе придут `missingFields` и уточняющие `questions`: кому нужен результат, какие есть ограничения, как измерить успех и как связаться с бизнесом. Анализ не сохраняет задачу.

### 2. Соберите карточку

Выполните `POST /api/tasks` с тем же черновиком и ответами:

```json
{
  "draftText": "Мы сеть из 12 кофеен в Алматы. Хотим понять, почему в будни после обеда падают продажи. Есть выгрузка чеков из кассовой системы за 2 года в Excel.",
  "industry": "HORECA",
  "answers": [
    {
      "field": "expectedResult",
      "answer": "Дашборд с продажами по часам и рекомендации по акциям."
    },
    {
      "field": "successCriteria",
      "answer": "Рост дневной выручки после обеда на 10% за 2 месяца."
    },
    {
      "field": "contact",
      "answer": "Операционный менеджер, ops@example.com"
    }
  ]
}
```

Ответ — `201 Created`, задача в статусе `DRAFT` и рейтинг **75/100 — `READY`**. Сохраните её `id`. Поля `users`, `constraints` и `interactionFormat` останутся пустыми, а `rating.tips` подскажет, что добавить.

### 3. Опубликуйте и получите отклик

1. При желании дополните карточку через `PUT /api/tasks/{id}/card`. Этот метод **заменяет все поля**: передавайте карточку целиком, иначе пропущенные поля станут пустыми.
2. Выполните `POST /api/tasks/{id}/publish` — задача появится в `GET /api/catalog`.
3. Получите команды через `GET /api/teams` и выберите `teamId`.
4. Отправьте `POST /api/tasks/{id}/proposals`, подставив выбранный идентификатор команды:

```json
{
  "teamId": 1,
  "idea": "Найдём часы падения продаж и предложим акции для каждой кофейни.",
  "plan": "Очистим выгрузку, исследуем продажи и соберём дашборд для пилота.",
  "duration": "4 недели",
  "prototypeUrl": ""
}
```

### 4. Подтвердите результат

Возьмите `id` созданного отклика из ответа:

```text
POST /api/proposals/{id}/accept
POST /api/proposals/{id}/confirm-milestone
```

Проверьте `GET /api/teams`: команда получила **+10 баллов**. Каждый вызов подтверждения добавляет один этап и ещё 10 баллов.

## Как устроен рейтинг

Рейтинг показывает полноту постановки задачи. Одинаковая карточка всегда получает одинаковую оценку: расчёт выполняет [`RatingService`](src/main/java/com/qadam/service/RatingService.java).

| Критерий | Максимум | Правило |
| --- | ---: | --- |
| Контекст и потребность | 20 | По 10 за каждое поле |
| Данные и материалы | 20 | Заполнено поле `data` |
| Ожидаемый результат | 15 | Заполнено поле `expectedResult` |
| Критерии успеха | 15 | Есть цифра или `%`; за текст без них — 7 |
| Ограничения | 10 | Заполнено поле `constraints` |
| Пользователи | 10 | Заполнено поле `users` |
| Связь с бизнесом | 10 | По 5 за контакт и формат взаимодействия |
| **Всего** | **100** | |

Поле засчитывается от 15 символов после удаления пробелов по краям; контакт — от 5. Название не приносит баллов. Проверка измеримости критериев — простая эвристика по наличию цифры или `%`.

| Баллы | Уровень | Название |
| --- | --- | --- |
| 0–39 | `DRAFT` | Черновик |
| 40–69 | `WORKING` | Рабочая задача |
| 70–89 | `READY` | Готова к работе |
| 90–100 | `PRIORITY` | Приоритетная |

**Статус публикации и уровень рейтинга независимы.** Можно опубликовать задачу с низким рейтингом: в каталоге она получит `needsClarification: true`. В рекомендации команд попадают только опубликованные задачи уровня `WORKING` и выше.

Рекомендации сопоставляют интересы, навыки и технологии команды с отраслью и текстом задачи. Алгоритм отбрасывает стоп-слова и сравнивает слова по первым пяти буквам. Ответ содержит `matchScore` и `matchedKeywords`, поэтому причину рекомендации можно проверить.

## ИИ и конфигурация

Настройки приложения — в [`application.yml`](src/main/resources/application.yml), шаблон окружения — в [`.env.example`](.env.example).

| Переменная | По умолчанию | Назначение |
| --- | --- | --- |
| `LLM_MODE` | `mock` | `mock` — локальная эвристика; `openai` — внешняя модель |
| `OPENAI_API_KEY` | Пусто | Обязателен для `LLM_MODE=openai` |
| `OPENAI_MODEL` | `gpt-4o-mini` | Модель для OpenAI-клиента проекта |
| `DEMO_DATA_ENABLED` | `true` | Загрузка демо-данных в пустую базу |

Для настройки Docker Compose скопируйте шаблон:

```bash
cp .env.example .env
```

Чтобы включить внешнюю модель, задайте в `.env` `LLM_MODE=openai` и свой `OPENAI_API_KEY`, затем запустите `docker compose up --build`. Файл `.env` исключён из Git.

**Maven не загружает `.env` автоматически.** При локальном запуске задавайте переменные через окружение терминала или конфигурацию запуска IDE. Например, отключить демо-данные в macOS / Linux:

```bash
DEMO_DATA_ENABLED=false ./mvnw spring-boot:run
```

### Где используется модель

| Операция | Поведение |
| --- | --- |
| Анализ черновика | Находит пробелы и формирует не меньше трёх уточняющих вопросов |
| Создание карточки | Раскладывает черновик и ответы по полям задачи |

В режиме `mock` предложения распределяются по ключевым словам, ответы добавляются в указанные поля. Это детерминированная реализация для разработки и демонстрации.

В режиме `openai` клиент вызывает Chat Completions через Spring `RestClient`, запрашивает JSON по строгой схеме и использует таймаут 60 секунд. Промпты предписывают использовать только исходные сведения и оставлять неизвестные поля пустыми. Проверка схемы и длины полей не гарантирует фактическую точность — карточку нужно просмотреть перед публикацией.

Невалидный ответ модели вызывает **одну повторную попытку**. Сетевые и HTTP-ошибки возвращаются без повтора. Если обработка не удалась, API отвечает `502`; задача не сохраняется. Вызов модели выполняется вне транзакции базы данных.

Промпты: [анализ](src/main/resources/prompts/analyze-task.md) · [сборка карточки](src/main/resources/prompts/build-card.md). Схемы: [анализ](src/main/resources/llm/task-analysis.schema.json) · [карточка](src/main/resources/llm/task-card.schema.json).

## API

Базовый путь — `/api`. Тела запросов и ответов — JSON. Полные схемы, ограничения полей и примеры доступны в [Swagger UI](http://localhost:8080/swagger-ui.html).

| Метод | Путь | Действие |
| --- | --- | --- |
| `GET` | `/health` | Проверка доступности |
| `GET` | `/industries` | Коды и названия отраслей |
| `POST` | `/tasks/analyze` | Анализ черновика без сохранения |
| `POST` | `/tasks` | Создание задачи в статусе `DRAFT` |
| `GET` | `/tasks/{id}` | Карточка, статус и рейтинг |
| `PUT` | `/tasks/{id}/card` | Полная замена карточки и пересчёт рейтинга |
| `POST` | `/tasks/{id}/publish` | Публикация задачи |
| `GET` | `/catalog?industry=HORECA&level=READY` | Каталог по убыванию рейтинга; оба фильтра необязательны |
| `GET` | `/teams` | Команды, навыки и баллы |
| `GET` | `/teams/{id}/recommendations` | Рекомендации задач для команды |
| `POST` | `/tasks/{id}/proposals` | Создание отклика |
| `GET` | `/tasks/{id}/proposals` | Отклики в порядке поступления |
| `POST` | `/proposals/{id}/accept` | Принятие отклика |
| `POST` | `/proposals/{id}/reject` | Отклонение отклика |
| `POST` | `/proposals/{id}/confirm-milestone` | Подтверждение этапа и начисление баллов |

Откликнуться можно только на опубликованную задачу. Число откликов, в том числе от одной команды, не ограничено. Бизнес может принять несколько команд. Решение по отклику доступно только из `PENDING`, подтверждение этапа — только для `ACCEPTED`.

<details>
<summary><strong>Валидация и формат ошибок</strong></summary>

Черновик должен содержать 20–5000 символов, отрасль обязательна. Допускается не больше 20 ответов с известными кодами полей. Поля карточки — до 3000 символов, название — до 200, контакт — до 300. Идея отклика — 10–2000 символов, план — 10–4000; срок обязателен, ссылка на прототип необязательна и должна начинаться с `http://` или `https://`.

```json
{
  "status": 404,
  "error": "Not Found",
  "message": "Задача с id=42 не найдена",
  "timestamp": "2026-09-23T10:15:30Z"
}
```

| Код | Причина |
| --- | --- |
| `400` | Невалидный запрос; ошибки отдельных полей передаются в `fieldErrors` |
| `404` | Задача, команда или отклик не найдены |
| `409` | Действие недоступно в текущем статусе |
| `502` | Не удалось обработать запрос через LLM |
| `500` | Непредвиденная ошибка сервера |

</details>

## Архитектура

Сервер разделён на контроллеры, сервисы и слой доступа к данным. Обе реализации LLM используют общий интерфейс, а расчёт рейтинга и рекомендации выполняются независимо от модели.

```text
Swagger / HTTP-клиент
         │
         ▼
    Controllers ─── валидация DTO и единый формат ошибок
         │
         ▼
     Services
         ├── TaskAiService ── LlmClient ── Mock / OpenAI
         ├── RatingService ── оценка полноты карточки
         ├── TaskMatcher ──── подбор задач по ключевым словам
         └── ProposalService ── отклики, этапы и баллы
         │
         ▼
  Spring Data JPA ── H2: Task, Team, Proposal
```

| Расположение | Что внутри |
| --- | --- |
| [`src/main/java/com/qadam`](src/main/java/com/qadam) | Пакеты `controller`, `service`, `repository`, `model`, `dto`, `config`, `llm` |
| [`src/main/resources/prompts`](src/main/resources/prompts) | Системные промпты |
| [`src/main/resources/llm`](src/main/resources/llm) | JSON-схемы ответов модели |
| [`src/main/resources/static`](src/main/resources/static) | Веб-прототип на HTML, CSS и JavaScript без сборщика |
| [`src/test/java/com/qadam`](src/test/java/com/qadam) | Модульные и интеграционные тесты сервера |
| [`.github/workflows/ci.yml`](.github/workflows/ci.yml) | Сборка, тесты и отчёт покрытия в GitHub Actions |
| [`Dockerfile`](Dockerfile) · [`docker-compose.yml`](docker-compose.yml) | Многоэтапная сборка, запуск от непривилегированного пользователя и health check |

## Разработка

### Сборка и тесты сервера

```bash
./mvnw clean verify
```

На Windows используйте `mvnw.cmd`. Команда собирает JAR, запускает тесты и создаёт отчёт JaCoCo в `target/site/jacoco/index.html`. После сборки приложение можно запустить отдельно:

```bash
java -jar target/qadam-0.0.1-SNAPSHOT.jar
```

Тесты проверяют сквозной сценарий задачи, рейтинг и его границы, рекомендации, правила откликов, валидацию, демо-данные, ошибки LLM и соответствие JSON-схем DTO. Они не обращаются к внешней модели; для скачивания зависимостей при первой сборке потребуется сеть.

GitHub Actions запускает `clean verify` на JDK 21 при push в `main` и для pull request. Отчёт JaCoCo сохраняется как артефакт `jacoco-report`; минимальный порог покрытия не задан. Docker-сборка пропускает тесты.

### Проверка модулей фронтенда

При установленном Node.js с поддержкой `node --test`:

```bash
# Бизнес-сценарий отдельного mock-сервиса
node --test src/main/resources/static/tests/business-flow.test.mjs

# Утилиты учебного прототипа, оставшиеся в репозитории
node --test src/test/frontend/lesson-utils.test.mjs
```

Эти тесты проверяют модули и не подтверждают работоспособность страницы с конфликтами слияния. В текущем CI запускаются только Java-тесты.

## Границы текущей версии

- **Авторизация и разграничение доступа не реализованы.** Роли бизнеса и команды описывают сценарий, но сервер не проверяет принадлежность действия пользователю.
- **Постоянного хранилища нет.** H2 работает в памяти; Docker Compose не добавляет сохранение данных между запусками.
- **Веб-интерфейс требует завершения интеграции.** Нужно разрешить конфликты слияния и связать бизнес-фасад с серверными DTO и методами.
- **Рейтинг оценивает заполненность.** Он не проверяет достоверность данных или экономическую ценность проекта.
- **Этапы подтверждаются счётчиком.** Каждый повторный запрос начисляет баллы; отдельной сущности этапа и защиты от повторного подтверждения одного этапа нет.

Эти ограничения задают следующие шаги развития MVP: завершить интерфейс, добавить пользователей и права доступа, постоянную базу данных и учёт отдельных этапов проекта.
